# @gwenjs/plugin-conformance

Static checks for a GWEN plugin or package.

## CLI

```bash
gwen-conformance check [--profile plugin|package] [--write] [--lockfile-base <ref>]
```

The default profile is `plugin`. `--write` rewrites `public-api.snap.json` from the build before the checks compare it (see `snapshot-values` and `snapshot-types`). `--lockfile-base <ref>` passes that ref as `lockfileBase`; the value is required, must not be empty, and must not start with `-`. Each option may be given at most once, in any order. Each finding is one line `<code> <file>:<line> <message>` (the file and `:<line>` are omitted when absent). The last line is `CONFORMANCE: <n> findings (<k> checks)`. The process returns 0 when `n` is 0, 1 when `n` is greater than 0, and 2 for an unknown command, an unknown option, a repeated option, or a `--lockfile-base` value that is missing, empty, or starts with `-`.

## Checks

- `exports` — every string target must start with `./` and be a file inside the package. `null` is skipped. A target that is not a string, an array, an object, or `null` is rejected. An empty `exports` object is rejected. Mixing subpath keys and condition keys is rejected. A target that contains `*` is not existence-checked. A target that resolves outside the package is rejected. In a condition object, `types` must be the first key. `./internal`, `./internal/…`, and any key that starts with `./internal*` are rejected in both profiles. Profile `plugin` also requires the `.` and `./module` subpaths. `exports` missing or not an object is rejected.
- `snapshot-values` and `snapshot-types` — compare `public-api.snap.json` with the built types of every subpath of `exports`, and write nothing, unless `--write` (or `write: true`) is given. The file lists `{ "<subpath>": { "values": string[], "types": string[] } }` with sorted names, in the gwen format. A value or type that is built and not listed (or listed and not built), a subpath of `exports` missing from the file (or the reverse), and a missing, invalid or malformed file are `SNAPSHOT_MISMATCH` findings; the file problem is one finding, reported by `snapshot-values` only. A subpath whose module entry (its `types` file, else its `types.import` file, else its `import` file) is not built is one finding too, and so is a subpath whose target names none of these files (`{ "default": … }`, a nested condition, an array). A `null` target is skipped. A target that is a pattern (`*`) or not a module entry (a `.wasm`, a `.css`) is never required. A snapshot file that exists but cannot be read is reported as `cannot be read (<code>)`, not as missing. A value name that starts with a single `_` in any subpath of `exports` (public or not) is a `PRIVATE_EXPORT` finding; names that start with `__` are skipped. In `checkPluginPackage`, both checks run only when `exports` has no finding; `checkSnapshot` does not run the `exports` check. With `--write`, the file is rewritten from the build before it is compared: 2-space JSON with a final newline, names sorted, `{ values, types }` per subpath. The keys keep the order of the old file, a new subpath follows in `exports` order, and a subpath no longer in `exports` is dropped; with no old file the keys are in `exports` order. It is left untouched when it already holds the same names, so a second write changes no byte. It is replaced through a temp file (`public-api.snap.json.tmp`), and a write that fails is one `SNAPSHOT_MISMATCH` finding, `public-api.snap.json cannot be written (<code>)`. A subpath whose target is not a module entry keeps its old entry. Nothing is written, and the findings are those of a read, while a subpath is not built or declares no types or import file, while `exports` names no subpath, or while the snapshot exists and cannot be read. `PRIVATE_EXPORT` is still reported after a write.
- `publint` — runs `publint --strict` on the package (warnings count as errors) and reports each message as a `PUBLINT` finding, with the publint text, on the `package.json` line of its field. A package that publint cannot pack or parse is one `PUBLINT` finding. Known limit: when publint cannot pack, it leaves one empty `publint-pack-*` directory in the temp directory per run (`@publint/pack` creates it before its `try`).
- `attw` — runs `attw --profile esm-only` on the tarball that `npm pack` makes, and reports each problem kind per entry point as an `ATTW` finding (per file when attw names a file and no entry point, for example `FalseCJS in "dist/index.d.cts"`). Problems that only concern the `node10` and `node16-cjs` resolutions are ignored, as the profile does. A package that ships no types, or that `npm pack` cannot pack, is one `ATTW` finding. The tarball is made with `npm pack --ignore-scripts`: lifecycle scripts do not run, unlike `attw --pack`, so build the package first. `npm` must be on the `PATH`. The `.attw.json` of the package is ignored: attw runs in a temp directory, so a package cannot exclude its own entry points from the check.
- `readme` — every name of `public-api.snap.json` (values and types, all subpaths) must appear in `README.md` as a whole identifier (`readyState` does not mention `ready`); the name `default` is never required. One `README_EXPORT_MISSING` finding per distinct name, for the first subpath that lists it. A missing `README.md` is one finding, and so is a `README.md` that cannot be read (`README.md cannot be read (<code>)`). It reads the snapshot after a write and runs only when `exports` has no finding.
- `imports` — reads every script file under `src` (not `*.d.ts`, not `node_modules`), every test file (see `test-mocks` for what a test file is), and the `.js`, `.mjs`, `.cjs`, `.d.ts`, `.d.mts` and `.d.cts` files under `dist` (internal specifiers only). Each `import`, `export … from`, `import("x")` (whatever follows its first argument), `require("x")`, `import x = require("x")` and `import("x")` type is a specifier, read with the TypeScript API. One finding per offending import line, and one `IMPORT_NOT_PUBLIC` per name. `@gwenjs/<package>/internal` and a `wasm` segment are `IMPORT_INTERNAL`, and so are those segments of a community base listed in `gwen.extends`. `@gwenjs/<package>/dist/…`, a `dist` or `src` segment of a community base listed in `gwen.extends`, a subpath that is not an entry of a framework package, a relative path that leaves the package root, and an absolute path (`/x.js`, `C:\x.js`) or a `file:` URL are `IMPORT_DEEP`. A `node:` builtin, a `#` alias and any other URL scheme (`https:`, `data:`) are not packages and are skipped. `@gwenjs/app`, `@gwenjs/vite`, `@gwenjs/physics2d`, `@gwenjs/physics3d` and `@gwenjs/physics3d-fracture`, and a test-only entry (`@gwenjs/core/testing`, `@gwenjs/core/node`, `@gwenjs/renderer-core/testing`) in `src`, are `IMPORT_FORBIDDEN_ENTRY`. Any other `@gwenjs/*` package (`@gwenjs/physics-core` included, until its snapshot ships; in a test file, `@gwenjs/plugin-conformance`, `@gwenjs/plugin-conformance/runtime` and `@gwenjs/plugin-conformance/vitest` are accepted, declared like a framework package, and any other subpath of it is `IMPORT_DEEP`), and an installed package (looked up in `node_modules` from the root and its ancestors) whose manifest has `gwen.type` `"plugin"` or lists `@gwenjs/core` as a peer or a dependency, are `IMPORT_FOREIGN_PLUGIN`. A community package (a name outside `@gwenjs/`) that lists a base verbatim in `gwen.extends` may import `<base>/extension`. The base is a package name (optional `@scope/` plus one segment), never a framework package or one of the forbidden packages above, which keep their own rules. Any other specifier of that base is `EXTENSION_ENTRY`, except that a test file may import the base root and `<base>/testing`. In `dist`, only an internal specifier of that base is reported. An official package keeps `IMPORT_FOREIGN_PLUGIN`. An entry that is not a package name, such as `@gwenjs/camera2d/sub`, is not a base. A name that a framework entry does not export (named import, re-export, default import, or a property read on a namespace import) is `IMPORT_NOT_PUBLIC`: the names come from `FRAMEWORK_ENTRIES`, and a module entry exports `default`. The same code is reported for a name imported from `<base>/extension` of a community base listed verbatim in `gwen.extends`, when that base is installed and its `package.json` parses. The names are the values and the types of the built `./extension` entry (`types`, then `types.import`, then `import`); a type-only named import is checked like a value import. A base that cannot be resolved, or whose `package.json` cannot be parsed, is not reported under this code, and a file under `dist` is not checked for these names. When the declared types file is not on disk, one finding on the specifier line says the specifier declares that path, which is not built. When the `./extension` target names no types file and no import file, one finding on the specifier line says so. A property read is matched by the name of the namespace, except where an enclosing function, block, `for` or `catch` rebinds that name (a parameter, a `var`, a `const` or `let`, a function or class declaration); a type position (`ns.Type`) is not affected by a rebinding. A framework package that `src` imports must be in `peerDependencies` (a test file may use `devDependencies` too; `dependencies` is not enough), or the line is `IMPORT_UNDECLARED`, reported only for an entry that is otherwise accepted. The package's own name and subpaths are always accepted. A package.json of `node_modules` that cannot be parsed is ignored. A file or a directory that cannot be read (any error but a missing one) rejects the promise. The check runs for both profiles.
- `augment` — reads every script file under `src`, every declaration file (`.d.ts`, `.d.mts`, `.d.cts`) under `src` or under a `tests`, `test` or `__tests__` directory, and every test file, once each: a file that is in two sets (`src/__tests__/a.ts`) is read once. `node_modules`, `dist` and dot directories are not walked, so a declaration file of `dist` is not read. A `declare module` whose name starts with `@gwenjs/`, other than `@gwenjs/schema` and other than the package's own name and its subpaths, is an `AUGMENT_TARGET` finding at the line of the declaration. A `GwenProvides` member (property or method signature, named by an identifier, a string, a number, or a computed string or template without substitution) added in a `declare module "@gwenjs/schema"` block is an `AUGMENT_TARGET` finding when the framework already declares that key; the message names the declaring package. The keys come from `src/framework-entries.generated.ts`, regenerated by `pnpm generate`. A `GwenProvides`, `GwenRuntimeHooks` or `GwenPluginRegistry` member is an `AUGMENT_TARGET` finding when an installed base's `./extension` declaration, or a declaration file it references inside the base directory, already declares that key. Those referenced declaration files are followed. The comparison is syntax only, and only for a community package: an official package is not compared with its bases. The message names the interface and the base. One finding per key. A framework `GwenProvides` key keeps the framework message when both match. A `GwenRuntimeHooks` member that no installed base declares is left to the `hooks` check. The files are parsed with the TypeScript API, so a declaration in a comment is not read. A file that cannot be read (any error but a missing one) rejects the promise. The check runs for both profiles.
- `test-mocks` — in a test file, a `mock` or `doMock` call of `vi` on an `@gwenjs/` package other than the package itself is a `TEST_MOCKS_FRAMEWORK` finding. A test file is any `*.test.*` or `*.spec.*` file, any file under a `tests`, `test` or `__tests__` directory, and any `*.setup.*` file at the package root (extensions `ts`, `tsx`, `mts`, `cts`, `js`, `jsx`, `mjs`, `cjs`; not `*.d.ts`); `node_modules`, `dist` and dot directories are not walked, and a mock call in another file of `src` is not read. The call is read as a `mock` call on `vi`, a `doMock` call on `vi`, element access on `vi` with the string `mock` or `doMock`, or the same on a renamed `vi` (named import from vitest), with a string, a template without substitution or `import("…")` as the first argument. A `vi` reached through `import * as vitest` is not read. Files named in the `setupFiles` of the config are not followed: only `*.setup.*` files at the package root are read as setup files. A `resolve.alias` or `test.alias` entry of `vitest.config.*` or `vite.config.*` at the root (`vitest.config.unit.ts` too) is a finding when its key is an `@gwenjs/` specifier: a string, a computed string, or a regular expression that starts with `@gwenjs/` (the own name, as a string or as the prefix of a regular expression, is exempt). The table is an object or an array of `{ find }` entries, written in place or as a `const` of the same file; an object literal or a same-file `const` object spread into the table is followed, and `alias` and `find` may be quoted. An alias key that cannot be read statically (a shorthand `{ find, replacement }`, a spread of a call) is not reported. The config file is parsed, not run. A directory that cannot be read (any error but a missing one) rejects the promise.
- `hooks` — reads `gwen.hookNamespace` and every `*.ts` file under `src` (not `*.d.ts`, not `node_modules`). The namespace must match `^[a-z][a-z0-9-]*$` and be neither a core-reserved nor a framework namespace; it is required when the package declares or emits a hook. A hook declared by `defineHooks({...})` (string-literal, identifier or numeric keys, or computed keys that name a same-file `const` string; a `const` string may be written with `as`, `satisfies` or parentheses, and a name that any other binding in the file shares is not resolved) or by a `GwenRuntimeHooks` augmentation of `@gwenjs/schema` must start with `<hookNamespace>:`. Each call of `emit`, `callHook`, `callHookParallel`, or `callHookWith` is an emit site: its name must be a string literal or a same-file `const` string, must not be in a reserved or framework namespace, must start with `<hookNamespace>:`, and must be declared in the package. An alias of an emit method is not an emit site. A listed base that is installed, whose `package.json` parses, and whose `gwen.hookNamespace` equals this package's is `HOOK_NAMESPACE_INVALID` on `package.json` line 1; the message names both. A base that cannot be resolved or parsed is left out of that comparison. The check runs for both profiles.
- `peers` — for each own key of `FRAMEWORK_RANGES`, a `peerDependencies` spec that is not that package's range (strict string equality, no semver parsing; the linked group uses `CORE_RANGE`) is `PEER_RANGE`, on the `package.json` line of the key. The same code is reported when the package is listed in `dependencies` or `optionalDependencies`, at any spec, except `@gwenjs/math`, which is accepted there. A `devDependencies` spec that is not an exact version (`major.minor.patch` with an optional prerelease and build, so a stack stamp passes; `^`, `~`, `*`, `latest`, `>=`, `1.x`, `workspace:`, `file:` and `npm:` do not) is `DEV_PIN`. A section that is not an object is skipped. A spec that is not a string is shown with `JSON.stringify`. A package outside `FRAMEWORK_RANGES` is ignored, except a base kept from `gwen.extends`: that base must be in `peerDependencies` on a usable semver range (not an any-range such as `*`, `x`, `X`, `x.x.x`, `>=0.0.0` or `>=0.0.0-0`, and not `latest`, an empty spec, or a `workspace:`, `file:`, `link:` or `npm:` spec), must not be in `dependencies` or `optionalDependencies`, and must have an exact `devDependencies` pin inside the range (prerelease included). Each problem is `EXTENSION_PEER`. A declared framework peer, or a base peer, that no non-test script or declaration file under `src` uses is `PEER_UNUSED`: a `declare module` of the package, a subpath import, `import type` and `export type … from` count as a use, `<base>/extension` counts as a use of the base, and a test-only import does not. `src` is read only when such a peer exists. The check runs for both profiles, even when `exports` has a finding.
- `manifest` — profile `plugin` requires `gwen.type` to be `"plugin"`. Both profiles require a non-empty `license` string and a `LICENSE`, `LICENSE.md`, or `LICENSE.txt` file. An official package (a name that starts with `@gwenjs/` and is not a framework package) that lists at least one valid, unique package name other than its own in `gwen.extends` is one `EXTENSION_OFFICIAL` finding, on the line of that key. A community package, a framework package, an absent field and an empty array produce no finding for that field. A malformed `gwen.extends` is a `MANIFEST` finding, for both profiles: the value is not an array (line of the key), an entry is not a string (line of that entry), a package name is listed twice (line of the later entry), the package lists its own name (line of that entry), or an entry is not a package name (optional `@scope/` plus one segment, no further `/`, no space, no uppercase; line of that entry). Each name kept in `gwen.extends` (a framework package name included) is `BASE_NOT_EXTENSIBLE`, for both profiles, when that base cannot be resolved from `node_modules` (this package and its ancestors), when its `package.json` cannot be parsed, when `exports` has no `"./extension"` entry (a string or a condition object counts), or when it has no `gwen.hookNamespace`. One finding per base per problem, on the line of that element. A base that cannot be resolved or parsed is not checked further. A missing, unreadable, or invalid `package.json` is one manifest finding, and the other checks do not run.
- `lockfile` — when `lockfileBase` is set, compares `pnpm-lock.yaml` with that git ref and reports one `LOCKFILE_DRIFT` finding per third-party package (a name outside `@gwenjs/`) that was added, removed, or resolved to another set of versions. The version is the text of a `packages:` or `snapshots:` key after `name@` and before the first `(`. The finding points at the first key of that name in the new file; a removed package points at `<ref>:pnpm-lock.yaml`. A `lockfileVersion` other than `9.0`, a missing lockfile, a ref that is empty, does not resolve or starts with `-`, or a git that cannot start is one `INVALID_SPEC` finding. The check runs for both profiles, and only when `lockfileBase` is set.

In `checkPluginPackage`, `imports`, `augment`, `hooks`, `test-mocks`, `peers` and `manifest` run even when `exports` has a finding. `publint` and `attw` run, like the snapshot and `readme` checks, only when `exports` has no finding: a missing target is already reported there. The report lists only the checks that ran.

## API

Exports of `@gwenjs/plugin-conformance`:

- `checkPluginPackage({ root, profile, write, lockfileBase })` runs the implemented checks (`exports`, `snapshot-values`, `snapshot-types`, `publint`, `attw`, `readme`, `imports`, `augment`, `hooks`, `test-mocks`, `peers`, `manifest`, `lockfile`) on the package at `root` and returns a `ConformanceReport`. An unknown `profile` (from a JS caller) returns no check and one `CONFORMANCE:INVALID_SPEC` finding that names the value and the allowed ones. A `src` file that cannot be read (any error but a missing file) rejects the promise with that error instead of passing silently.
- `checkSnapshot`, called as `checkSnapshot(pkgRoot, { write })`, compares `public-api.snap.json` with the built package at `pkgRoot` and returns a `ConformanceReport` for `snapshot-values` and `snapshot-types`. It reads the package and writes nothing unless `write` is `true`, which rewrites the snapshot first.
- `runComposableSurfaceSuite(entry, { allow })` registers the composable surface rows of a package entry in the current vitest suite, inside a `composable surface` describe. The row `every function export matches a prefix rule` fails on a function export (classes are skipped) whose name does not match `^(define|use|on|place|create|get|with)[A-Z]`, unless it is in `allow`. An `allow` name that is not a function export fails the same row; a name that already follows the prefix rule is accepted and has no effect. The row `<name> outside any context throws GwenContextError` is registered for each `use*` and `on*` function export: it calls the export with no argument and requires an instance of `GwenContextError` from `@gwenjs/kit`. The package needs `vitest` and `@gwenjs/kit` installed: both are required peer dependencies, because the main entry imports `vitest`.
- `ComposableSurfaceOptions` is the input of `runComposableSurfaceSuite`: the optional `allow`, a list of function export names exempt from the prefix rule.
- `FRAMEWORK_PLUGIN_NAMES` is the frozen list of plugin names built by public factories: `CameraCorePlugin` (`packages/camera-core/src/camera-core-plugin.ts:56`), the viewports plugin (`packages/app/src/viewports-plugin.ts:35`), the screen plugin (`packages/renderer-core/src/screen-plugin.ts:55`), and the scene plugin `createRealEngine({ scenes: true })` installs (`packages/core/src/testing/create-real-engine.ts:93`, `packages/core/src/scene/engine-plugin.ts:113`). `gwen:tween` is not in the list: `TweenPlugin` is not a public factory (`packages/core/src/internal.ts:68`), and no official plugin should name it.
- `FRAMEWORK_ENTRIES` maps each framework entry a plugin may import (`@gwenjs/core`, `@gwenjs/core/system`, `@gwenjs/kit/plugin`, …) to the sorted names it exports, values and types. It also holds the entries that only tests may import: `@gwenjs/core/testing`, `@gwenjs/core/node` and `@gwenjs/renderer-core/testing`. It is generated by `scripts/generate-framework-entries.mjs` from the `public-api.snap.json` files of the framework packages, and never listed by hand. `prebuild` runs the script with `--check` and fails, naming the file, when the committed `src/framework-entries.generated.ts` is stale; `pnpm generate` rewrites it. A framework package with no snapshot is left out.
- `ConformanceErrorCodes` holds the codes: `ATTW`, `AUGMENT_TARGET`, `BASE_NOT_EXTENSIBLE`, `DEV_PIN`, `EXPORTS_INVALID`, `EXTENSION_ENTRY`, `EXTENSION_OFFICIAL`, `EXTENSION_PEER`, `HOOK_DYNAMIC_NAME`, `HOOK_FOREIGN_NAMESPACE`, `HOOK_NAMESPACE_INVALID`, `HOOK_RESERVED`, `HOOK_UNDECLARED`, `IMPORT_DEEP`, `IMPORT_FORBIDDEN_ENTRY`, `IMPORT_FOREIGN_PLUGIN`, `IMPORT_INTERNAL`, `IMPORT_NOT_PUBLIC`, `IMPORT_UNDECLARED`, `LOCKFILE_DRIFT`, `MANIFEST`, `INVALID_SPEC`, `PEER_RANGE`, `PEER_UNUSED`, `PRIVATE_EXPORT`, `PUBLINT`, `README_EXPORT_MISSING`, `RUNTIME_COMPOSABLE_CONTEXT`, `RUNTIME_DEV_WARNING`, `RUNTIME_FRAME_EVENT`, `RUNTIME_MODULE`, `RUNTIME_REQUIRES`, `RUNTIME_SHAPE`, `RUNTIME_TEARDOWN`, `RUNTIME_TWO_ENGINES`, `RUNTIME_PROVIDES`, `RUNTIME_REENTRY`, `RUNTIME_REMOVE_LEAK`, `RUNTIME_OPTIONS`, `RUNTIME_PER_ENTITY_PATH`, `SNAPSHOT_MISMATCH`, `TEST_MOCKS_FRAMEWORK`. Each value is prefixed `CONFORMANCE:`.
- `CheckPluginPackageOptions` is the input of `checkPluginPackage`: `root`, `profile` (`plugin` or `package`), the optional `write` (rewrite the snapshot before comparing it), and the optional `lockfileBase`, the git ref of the lockfile to compare with. The `lockfile` check runs only when it is set.
- `ConformanceCheckId` is the id of a check, in check order.
- `ConformanceCode` is one value of `ConformanceErrorCodes`.
- `ConformanceFinding` is one problem: `code`, `message`, `hint`, and an optional `file` and `line`.
- `ConformanceReport` is the result: `checks` (the checks that ran) and `findings`.
- `runPluginConformance` (`runPluginConformance(spec)`) on `@gwenjs/plugin-conformance/runtime` takes a `PluginConformanceSpec` and returns a `RuntimeConformanceReport` whose `checks` are `RuntimeCheckId` values. The spec fields and the `INVALID_SPEC` rules are under Runtime. The runtime checks are listed there too.
- `describePluginConformance` (`describePluginConformance(spec)`) from `@gwenjs/plugin-conformance/vitest` registers one row per runtime check in the current vitest suite.

## Quick start

A plugin repository adds one test file:

```ts
import { describePluginConformance } from "@gwenjs/plugin-conformance/vitest";

describePluginConformance({ packageName: "@scope/plugin", factories: [{ export: "Plugin" }] });
```

## Runtime

`runPluginConformance(spec)` validates `spec` and loads the built package at `spec.root` (the process working directory when `root` is not set). It does not throw. A valid spec runs the runtime checks below. `checks` lists the ones that ran, in check order, and `findings` lists what they reported. A problem in the spec or in the load is one or more `CONFORMANCE:INVALID_SPEC` findings, sorted by file, line, code, then message, and `checks` stays empty. An invalid spec is returned without loading the package. A `frameworkProviders` factory that throws, or whose plugin name is not in `FRAMEWORK_PLUGIN_NAMES`, is the same code and `checks` stays empty. A `fixture` that throws is the same code, reported by the `frames` check, so `checks` lists the checks that ran. A `fixture` or a module `setup` that never resolves is not time-bounded. The vitest `testTimeout` applies.

- `PluginConformanceSpec` fields: `packageName` (a non-empty string, equal to the `name` of `package.json`), `factories` (a non-empty `PluginFactorySpec` list; each `export` is a non-empty string), optional `root`, optional `official`, optional `frameworkProviders`, optional `fixture`, optional `frames` (an integer greater than or equal to 1; the default is 3), optional `variant` (`"light"`, `"physics2d"`, or `"physics3d"`), optional `bases` (a list of `{ packageName, export }`; `packageName` and `export` are non-empty strings; `options` is optional).
- The loader reads `<root>/package.json`. No `package.json`, a file that cannot be read, a file that is not valid JSON, a `name` that is not a non-empty string, or `exports` that is not an object, is `INVALID_SPEC`. It reads `exports["."].import`, and `exports["./module"].import` when that subpath is present. Each target must be a non-empty string that starts with `./` and resolves to a file under the package root. A target outside the root, a target under `<root>/src`, or a target that is not a file is `INVALID_SPEC`. The loader dynamic-imports only the root entry and does not read `<root>/src`. A factory `export` that the built entry does not export is `INVALID_SPEC`, and the message names that export. A `packageName` that differs from `package.json` `name` is `INVALID_SPEC`, and the message names both. A bad `frames` message names `frames` and the minimum 1. A bad `variant` message lists `light`, `physics2d`, and `physics3d`. An empty `factories` list message names `factories`. `bases`, when set, must be a list of objects with non-empty string `packageName` and `export`. A `spec.bases` package outside the transitive closure of `gwen.extends` is `INVALID_SPEC`, and the message names that package and `gwen.extends`. A name in `gwen.extends` with no `spec.bases` entry is `INVALID_SPEC`, and the message names that package and `spec.bases`. A `spec.bases` package that is not installed under the package root or an ancestor is `INVALID_SPEC`, and the message names the package and the root. A `spec.bases` export that is not a function is `INVALID_SPEC`, and the message names that export.

### Runtime checks

- `shape` — the export is a function, the return is a plugin, and its own keys are in `GWEN_PLUGIN_KEYS` from `@gwenjs/schema`. An export that is not a function, a factory that throws, a return that is not a plugin, or a key outside that list, for example `onUpdate`, is one `RUNTIME_SHAPE` finding. The message names the package and the export. Other checks stay silent for that export. Fix. Export a function that returns a plugin, and remove the extra key.
- `requires` — runs for every factory. `frameworkProviders` are installed, then a sibling factory of this package when `requires.plugins` names it, then `engine.use`. The installed plugins must be that baseline plus its name. An extra name is one `RUNTIME_REQUIRES` finding, and the message lists the installed plugins. A `use` rejection that is not the engine dependency code and not a provide code is one finding, and the message carries the engine code, when there is one, and the thrown text. When that dependency error names no entry this check still allows, the check stays silent.
