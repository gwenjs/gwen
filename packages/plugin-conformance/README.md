# @gwenjs/plugin-conformance

Static checks for a GWEN plugin or package.

## CLI

```bash
gwen-conformance check [--profile plugin|package] [--write]
```

The default profile is `plugin`. `--write` rewrites `public-api.snap.json` from the build before the checks compare it (see `snapshot-values` and `snapshot-types`). Each option may be given at most once, in any order. Each finding is one line `<code> <file>:<line> <message>` (the file and `:<line>` are omitted when absent). The last line is `CONFORMANCE: <n> findings (<k> checks)`. The process returns 0 when `n` is 0, 1 when `n` is greater than 0, and 2 for an unknown command, an unknown option or a repeated option.

## Checks

- `exports` — every string target must start with `./` and be a file inside the package. `null` is skipped. A target that is not a string, an array, an object, or `null` is rejected. An empty `exports` object is rejected. Mixing subpath keys and condition keys is rejected. A target that contains `*` is not existence-checked. A target that resolves outside the package is rejected. In a condition object, `types` must be the first key. `./internal`, `./internal/…`, and any key that starts with `./internal*` are rejected in both profiles. Profile `plugin` also requires the `.` and `./module` subpaths. `exports` missing or not an object is rejected.
- `snapshot-values` and `snapshot-types` — compare `public-api.snap.json` with the built types of every subpath of `exports`, and write nothing, unless `--write` (or `write: true`) is given. The file lists `{ "<subpath>": { "values": string[], "types": string[] } }` with sorted names, in the gwen format. A value or type that is built and not listed (or listed and not built), a subpath of `exports` missing from the file (or the reverse), and a missing, invalid or malformed file are `SNAPSHOT_MISMATCH` findings; the file problem is one finding, reported by `snapshot-values` only. A subpath whose module entry (its `types` file, else its `types.import` file, else its `import` file) is not built is one finding too, and so is a subpath whose target names none of these files (`{ "default": … }`, a nested condition, an array). A `null` target is skipped. A target that is a pattern (`*`) or not a module entry (a `.wasm`, a `.css`) is never required. A snapshot file that exists but cannot be read is reported as `cannot be read (<code>)`, not as missing. A value name that starts with a single `_` in any subpath of `exports` (public or not) is a `PRIVATE_EXPORT` finding; names that start with `__` are skipped. In `checkPluginPackage`, both checks run only when `exports` has no finding; `checkSnapshot` does not run the `exports` check. With `--write`, the file is rewritten from the build before it is compared: 2-space JSON with a final newline, names sorted, `{ values, types }` per subpath. The keys keep the order of the old file, a new subpath follows in `exports` order, and a subpath no longer in `exports` is dropped; with no old file the keys are in `exports` order. It is left untouched when it already holds the same names, so a second write changes no byte. It is replaced through a temp file (`public-api.snap.json.tmp`), and a write that fails is one `SNAPSHOT_MISMATCH` finding, `public-api.snap.json cannot be written (<code>)`. A subpath whose target is not a module entry keeps its old entry. Nothing is written, and the findings are those of a read, while a subpath is not built or declares no types or import file, while `exports` names no subpath, or while the snapshot exists and cannot be read. `PRIVATE_EXPORT` is still reported after a write.
- `publint` — runs `publint --strict` on the package (warnings count as errors) and reports each message as a `PUBLINT` finding, with the publint text, on the `package.json` line of its field. A package that publint cannot pack or parse is one `PUBLINT` finding. Known limit: when publint cannot pack, it leaves one empty `publint-pack-*` directory in the temp directory per run (`@publint/pack` creates it before its `try`).
- `attw` — runs `attw --profile esm-only` on the tarball that `npm pack` makes, and reports each problem kind per entry point as an `ATTW` finding (per file when attw names a file and no entry point, for example `FalseCJS in "dist/index.d.cts"`). Problems that only concern the `node10` and `node16-cjs` resolutions are ignored, as the profile does. A package that ships no types, or that `npm pack` cannot pack, is one `ATTW` finding. The tarball is made with `npm pack --ignore-scripts`: lifecycle scripts do not run, unlike `attw --pack`, so build the package first. `npm` must be on the `PATH`. The `.attw.json` of the package is ignored: attw runs in a temp directory, so a package cannot exclude its own entry points from the check.
- `readme` — every name of `public-api.snap.json` (values and types, all subpaths) must appear in `README.md` as a whole identifier (`readyState` does not mention `ready`); the name `default` is never required. One `README_EXPORT_MISSING` finding per distinct name, for the first subpath that lists it. A missing `README.md` is one finding, and so is a `README.md` that cannot be read (`README.md cannot be read (<code>)`). It reads the snapshot after a write and runs only when `exports` has no finding.
- `imports` — reads every script file under `src` (not `*.d.ts`, not `node_modules`), every test file (see `test-mocks` for what a test file is), and the `.js`, `.mjs`, `.cjs`, `.d.ts`, `.d.mts` and `.d.cts` files under `dist` (internal specifiers only). Each `import`, `export … from`, `import("x")` (whatever follows its first argument), `require("x")`, `import x = require("x")` and `import("x")` type is a specifier, read with the TypeScript API. One finding per offending import line, and one `IMPORT_NOT_PUBLIC` per name. `@gwenjs/<package>/internal` and a `wasm` segment are `IMPORT_INTERNAL`. `@gwenjs/<package>/dist/…`, a subpath that is not an entry of a framework package, a relative path that leaves the package root, and an absolute path (`/x.js`, `C:\x.js`) or a `file:` URL are `IMPORT_DEEP`. A `node:` builtin, a `#` alias and any other URL scheme (`https:`, `data:`) are not packages and are skipped. `@gwenjs/app`, `@gwenjs/vite`, `@gwenjs/physics2d`, `@gwenjs/physics3d` and `@gwenjs/physics3d-fracture`, and a test-only entry (`@gwenjs/core/testing`, `@gwenjs/core/node`, `@gwenjs/renderer-core/testing`) in `src`, are `IMPORT_FORBIDDEN_ENTRY`. Any other `@gwenjs/*` package (`@gwenjs/physics-core` included, until its snapshot ships; in a test file, `@gwenjs/plugin-conformance`, `@gwenjs/plugin-conformance/runtime` and `@gwenjs/plugin-conformance/vitest` are accepted, declared like a framework package, and any other subpath of it is `IMPORT_DEEP`), and an installed package (looked up in `node_modules` from the root and its ancestors) whose manifest has `gwen.type` `"plugin"` or lists `@gwenjs/core` as a peer or a dependency, are `IMPORT_FOREIGN_PLUGIN`. A community package (a name outside `@gwenjs/`) may import `<base>/extension` of a package `<base>` listed in `gwen.extends`: `<base>` is a package name with no subpath, and never a framework package or one of the forbidden packages above, which keep their own rules. A name that a framework entry does not export (named import, re-export, default import, or a property read on a namespace import) is `IMPORT_NOT_PUBLIC`: the names come from `FRAMEWORK_ENTRIES`, and a module entry exports `default`. A property read is matched by the name of the namespace, except where an enclosing function, block, `for` or `catch` rebinds that name (a parameter, a `var`, a `const` or `let`, a function or class declaration); a type position (`ns.Type`) is not affected by a rebinding. A framework package that `src` imports must be in `peerDependencies` (a test file may use `devDependencies` too; `dependencies` is not enough), or the line is `IMPORT_UNDECLARED`, reported only for an entry that is otherwise accepted. The package's own name and subpaths are always accepted. A package.json of `node_modules` that cannot be parsed is ignored. A file or a directory that cannot be read (any error but a missing one) rejects the promise. The check runs for both profiles.
- `augment` — reads every script file under `src`, every declaration file (`.d.ts`, `.d.mts`, `.d.cts`) under `src` or under a `tests`, `test` or `__tests__` directory, and every test file, once each: a file that is in two sets (`src/__tests__/a.ts`) is read once. `node_modules`, `dist` and dot directories are not walked, so a declaration file of `dist` is not read. A `declare module` whose name starts with `@gwenjs/`, other than `@gwenjs/schema` and other than the package's own name and its subpaths, is an `AUGMENT_TARGET` finding at the line of the declaration. A `GwenProvides` member (property or method signature, named by an identifier, a string, a number, or a computed string or template without substitution) added in a `declare module "@gwenjs/schema"` block is an `AUGMENT_TARGET` finding when the framework already declares that key; the message names the declaring package. The keys come from `src/framework-entries.generated.ts`, regenerated by `pnpm generate`. A `GwenRuntimeHooks` member is left to the `hooks` check. The files are parsed with the TypeScript API, so a declaration in a comment is not read. A file that cannot be read (any error but a missing one) rejects the promise. The check runs for both profiles.
- `test-mocks` — in a test file, a `mock` or `doMock` call of `vi` on an `@gwenjs/` package other than the package itself is a `TEST_MOCKS_FRAMEWORK` finding. A test file is any `*.test.*` or `*.spec.*` file, any file under a `tests`, `test` or `__tests__` directory, and any `*.setup.*` file at the package root (extensions `ts`, `tsx`, `mts`, `cts`, `js`, `jsx`, `mjs`, `cjs`; not `*.d.ts`); `node_modules`, `dist` and dot directories are not walked, and a mock call in another file of `src` is not read. The call is read as a `mock` call on `vi`, a `doMock` call on `vi`, element access on `vi` with the string `mock` or `doMock`, or the same on a renamed `vi` (named import from vitest), with a string, a template without substitution or `import("…")` as the first argument. A `vi` reached through `import * as vitest` is not read. Files named in the `setupFiles` of the config are not followed: only `*.setup.*` files at the package root are read as setup files. A `resolve.alias` or `test.alias` entry of `vitest.config.*` or `vite.config.*` at the root (`vitest.config.unit.ts` too) is a finding when its key is an `@gwenjs/` specifier: a string, a computed string, or a regular expression that starts with `@gwenjs/` (the own name, as a string or as the prefix of a regular expression, is exempt). The table is an object or an array of `{ find }` entries, written in place or as a `const` of the same file; an object literal or a same-file `const` object spread into the table is followed, and `alias` and `find` may be quoted. An alias key that cannot be read statically (a shorthand `{ find, replacement }`, a spread of a call) is not reported. The config file is parsed, not run. A directory that cannot be read (any error but a missing one) rejects the promise.
- `hooks` — reads `gwen.hookNamespace` and every `*.ts` file under `src` (not `*.d.ts`, not `node_modules`). The namespace must match `^[a-z][a-z0-9-]*$` and be neither a core-reserved nor a framework namespace; it is required when the package declares or emits a hook. A hook declared by `defineHooks({...})` (string-literal, identifier or numeric keys, or computed keys that name a same-file `const` string; a `const` string may be written with `as`, `satisfies` or parentheses, and a name that any other binding in the file shares is not resolved) or by a `GwenRuntimeHooks` augmentation of `@gwenjs/schema` must start with `<hookNamespace>:`. Each call of `emit`, `callHook`, `callHookParallel`, or `callHookWith` is an emit site: its name must be a string literal or a same-file `const` string, must not be in a reserved or framework namespace, must start with `<hookNamespace>:`, and must be declared in the package. An alias of an emit method is not an emit site. The check runs for both profiles.
- `manifest` — profile `plugin` requires `gwen.type` to be `"plugin"`. Both profiles require a non-empty `license` string and a `LICENSE`, `LICENSE.md`, or `LICENSE.txt` file. A missing, unreadable, or invalid `package.json` is one manifest finding, and the other checks do not run.

In `checkPluginPackage`, `imports`, `augment`, `hooks`, `test-mocks` and `manifest` run even when `exports` has a finding. `publint` and `attw` run, like the snapshot and `readme` checks, only when `exports` has no finding: a missing target is already reported there. The report lists only the checks that ran.

## API

Exports of `@gwenjs/plugin-conformance`:

- `checkPluginPackage({ root, profile, write })` runs the implemented checks (`exports`, `snapshot-values`, `snapshot-types`, `publint`, `attw`, `readme`, `imports`, `augment`, `hooks`, `test-mocks`, `manifest`) on the package at `root` and returns a `ConformanceReport`. An unknown `profile` (from a JS caller) returns no check and one `CONFORMANCE:INVALID_SPEC` finding that names the value and the allowed ones. A `src` file that cannot be read (any error but a missing file) rejects the promise with that error instead of passing silently.
- `checkSnapshot`, called as `checkSnapshot(pkgRoot, { write })`, compares `public-api.snap.json` with the built package at `pkgRoot` and returns a `ConformanceReport` for `snapshot-values` and `snapshot-types`. It reads the package and writes nothing unless `write` is `true`, which rewrites the snapshot first.
- `runComposableSurfaceSuite(entry, { allow })` registers the composable surface rows of a package entry in the current vitest suite, inside a `composable surface` describe. The row `every function export matches a prefix rule` fails on a function export (classes are skipped) whose name does not match `^(define|use|on|place|create|get|with)[A-Z]`, unless it is in `allow`. An `allow` name that is not a function export fails the same row; a name that already follows the prefix rule is accepted and has no effect. The row `<name> outside any context throws GwenContextError` is registered for each `use*` and `on*` function export: it calls the export with no argument and requires an instance of `GwenContextError` from `@gwenjs/kit`. The package needs `vitest` and `@gwenjs/kit` installed: both are required peer dependencies, because the main entry imports `vitest`.
- `ComposableSurfaceOptions` is the input of `runComposableSurfaceSuite`: the optional `allow`, a list of function export names exempt from the prefix rule.
- `FRAMEWORK_ENTRIES` maps each framework entry a plugin may import (`@gwenjs/core`, `@gwenjs/core/system`, `@gwenjs/kit/plugin`, …) to the sorted names it exports, values and types. It also holds the entries that only tests may import: `@gwenjs/core/testing`, `@gwenjs/core/node` and `@gwenjs/renderer-core/testing`. It is generated by `scripts/generate-framework-entries.mjs` from the `public-api.snap.json` files of the framework packages, and never listed by hand. `prebuild` runs the script with `--check` and fails, naming the file, when the committed `src/framework-entries.generated.ts` is stale; `pnpm generate` rewrites it. A framework package with no snapshot is left out.
- `ConformanceErrorCodes` holds the codes: `ATTW`, `AUGMENT_TARGET`, `EXPORTS_INVALID`, `HOOK_DYNAMIC_NAME`, `HOOK_FOREIGN_NAMESPACE`, `HOOK_NAMESPACE_INVALID`, `HOOK_RESERVED`, `HOOK_UNDECLARED`, `IMPORT_DEEP`, `IMPORT_FORBIDDEN_ENTRY`, `IMPORT_FOREIGN_PLUGIN`, `IMPORT_INTERNAL`, `IMPORT_NOT_PUBLIC`, `IMPORT_UNDECLARED`, `MANIFEST`, `INVALID_SPEC`, `PRIVATE_EXPORT`, `PUBLINT`, `README_EXPORT_MISSING`, `SNAPSHOT_MISMATCH`, `TEST_MOCKS_FRAMEWORK`. Each value is prefixed `CONFORMANCE:`.
- `CheckPluginPackageOptions` is the input of `checkPluginPackage`: `root`, `profile` (`plugin` or `package`), the optional `write` (rewrite the snapshot before comparing it), and the optional `lockfileBase`, which is accepted and not used yet.
- `ConformanceCheckId` is the id of a check, in check order.
- `ConformanceCode` is one value of `ConformanceErrorCodes`.
- `ConformanceFinding` is one problem: `code`, `message`, `hint`, and an optional `file` and `line`.
- `ConformanceReport` is the result: `checks` (the checks that ran) and `findings`.
